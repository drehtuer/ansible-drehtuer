== Future work (not urgent)

* *No umbrella playbook.* There is a `playbooks/<role>.yml` per role but nothing that runs them all in the right order for a fresh host (e.g. `system`/`apt`/`users` before service roles). Running playbooks individually is the deliberate workflow for now (easier to test each role in isolation while the configuration is still being built, and a full reinstall isn't currently needed). Worth adding a `playbooks/site.yml` (or an `invoke` task that chains the individual playbooks in order) once the roles have settled, so a full rebuild becomes a single command — relevant to the repo's migration goal, but not blocking current work. Each playbook's role is already tagged with its own name (e.g. `apt`, `mail`) specifically so a future umbrella gets selective `--tags`/`--skip-tags` runs for free, without a follow-up pass through every playbook. Six separate ordering constraints are waiting on it - `apt` before everything, `dns` before `spam`, `database` before `cloud`, `docker`/`fail2ban`/`http` before `fail2ban_ui`, `docker`/`http`/`mail` before `monitoring`, and `http` before `fail2ban` (whose nginx jails refuse to start until nginx has created the logs they watch) - each written up under *Role ordering constraints* in `doc/STATUS.adoc`.
+
The order itself no longer has to be invented: `.claude/skills/testlab/lab.sh` carries it as its `PLAYBOOKS` array and has run in that order against a real guest, so `site.yml` has a tested starting point rather than a guess. Note what that array leaves out, which is a gap in its own right - `nsd`, `fail2ban_ui` and `talk` are absent from the default deploy and only run when named explicitly, so "every playbook, in order" currently means seventeen of the twenty roles that should run in a rebuild (`upgrade` is the twenty-first and is excluded on purpose, being tagged `never`).
* *Every playbook still targets `hosts: all`.* The second host (`nyarlathotep`, see `doc/TESTING.adoc`) arrived before the playbooks were regrouped, so the inventory now has `production` and `testlab` groups but the playbooks themselves are unchanged. What keeps a run off the wrong machine is `invoke run-playbook` refusing to run without `--hosts` — a guard, not a fix. The fix is to give each playbook a group, which matters properly once a host exists that should *not* run every role (e.g. one that does no mail/spam/imap). Worth doing alongside the umbrella playbook above, since both touch the same files.
* *`roles/talk` depends on `roles/docker`, `roles/http` and `roles/cloud`.* The engine and Compose v2, nginx plus a certificate covering `talk.subdomain`, and the Nextcloud it registers itself with through `occ`. Nothing asserts it; one more ordering constraint for the umbrella playbook. The certificate half of that pairing is satisfied - `talk` is in `http.letsencrypt.subdomains` alongside `f2b`, `spam` and `status` - but nothing enforces the pairing, so it stays true only for as long as someone remembers it.
* *SMTP and IMAP authenticate with passwords only; client certificates were never considered.* Both ends already go through one place, which makes this smaller than it looks: Postfix delegates SASL to Dovecot (`smtpd_sasl_type = dovecot`, `smtpd_sasl_path = private/auth`), and Dovecot authenticates against system accounts (`passdb pam`, `userdb passwd`, `auth_mechanisms = plain login`). Moving to certificates means `auth_ssl_require_client_cert` and `auth_ssl_username_from_cert` in Dovecot, and both protocols follow. **The trap is the CA.** `imap.conf.ssl.ca` currently points at Let's Encrypt's chain because that is what serving the certificate needs; reusing it to *validate* clients would mean every certificate Let's Encrypt has ever issued authenticates as a local user. This needs a private CA of its own, with issuance, renewal and revocation to run — which is the real cost, not the Dovecot settings. Weigh also that client-certificate support in mail clients is uneven, especially on mobile, and that certificates-only means no fallback: a lost device is a lockout rather than a password reset.
* *No rendered documentation, though the docs were written for it.* Every page under `doc/` opens with `include::.attributes-page.adoc[]`, and that file already sets `:backend: html5`, `:data-uri:`, `:toc: auto` and a source highlighter — so the intent to render standalone HTML pages predates this note, and only the build and publish step is missing. asciidoctor is now installed and invoked — `invoke lint-docs` and the `AsciiDoc` job in `lint.yml` both run it — but only as a *structural check*, with output to `/dev/null`. Nothing renders the pages to anything anybody can read, and there is no publish step or third workflow. A third workflow rendering `doc/*.adoc` to GitHub Pages would cost little and pay off most on `STATUS.adoc`, which is long, heavily cross-referenced and much easier to navigate with the table of contents it already asks for. Note there is no disclosure question to weigh: the repository is already public, so this changes how the documentation reads, not who can read it.

== Verify / likely bugs

* *`podcast` fails the code integrity check and cannot be repaired.* Its two `dist/screenshot*.png` were re-encoded by the PNG cron job removed on 2026-08-16, and one was truncated to zero bytes. Re-downloading is not possible: the app store gives the release's download URL as a GitLab CI artifact which now returns 404, and `app:update` offers nothing newer, so version 0.3.1 cannot be fetched again. The affected files are screenshots - cosmetic, unused at run time - and the app is disabled. So this is a choice rather than a fault to fix: leave the warning, or `occ app:remove podcast`, which is defensible given the app is disabled and its upstream source has gone. Nothing else is affected; core and `files_archive` were both repaired and check clean.


* *The SPF reject path is proven; the DKIM one is not.* `roles/spam/files/rspamd/force_actions.conf` rejects on `R_SPF_FAIL` and `R_DKIM_REJECT`. The SPF half was confirmed against real inbound mail on 2026-08-16: two messages carrying `R_SPF_FAIL` were answered `T (reject)`, and one of them scored *3.80 against a required 6.00* - below the spam threshold, so score-based logic would have taken no action and something must have forced it, which is exactly what that file does. `R_DKIM_REJECT` has never appeared on a real message, only in RSpamd's startup lines registering the symbol, so that half remains unexercised.
+
Note the evidence is perishable: RSpamd's log rotates daily keeping four generations, and the lines above had already rotated away hours later. Anyone re-checking should not read an empty log as an absence of rejections - capture the evidence when it appears, or lengthen the retention first.

* *The CSP still permits inline script and style.* `roles/http/files/security.conf` was narrowed from a policy that allowed any `http:`/`https:` origin to one scoped to this origin, but `'unsafe-inline'` remains for both script and style because the RSpamd web UI proxied at `spam.<domain>` includes the same file and needs them. Removing them means either giving that vhost its own policy or testing the UI in a browser afterwards - a 200 from `curl` does not prove the interface still works. The per-vhost route now has a worked example to copy: `roles/monitoring` repeats the entire header set inside its `location /` with `'unsafe-eval'` and `blob:` added, because nginx drops every inherited `add_header` the moment a block declares one of its own. Doing the same for `spam.<domain>` would let the shared file lose `'unsafe-inline'` for everything else — and the check that it worked is still a browser.


* *Re-check the fail2ban UI's config handling when it is next upgraded.* It and `roles/fail2ban` both write `jail.local`, the role wins, and the alternatives were investigated on 2026-08-16 and deliberately rejected - the reasoning is in `doc/STATUS.adoc` and does not need repeating. What would settle it properly is an upstream option to target a specific file, or a genuine read-only mode; check for either on the next image bump.


* *The `http` role never removes a vhost dropped from `http.sites`.* It renders and enables that list, but nothing deletes a site that has left it, so the old `sites-available`/`sites-enabled` pair stays on disk and keeps being served. That is how a name can end up claimed by two vhosts at once, which nginx resolves by keeping whichever loaded first and emitting a `conflicting server name` warning — and `nginx -t` reports the result as a success, so neither the role nor `invoke check-drift` notices. Hit for real when `roles/monitoring` took `status.<domain>` over from a static placeholder; that role deletes the specific file itself, which fixes the instance and not the class. The general fix is for the `http` role to own the whole of `sites-enabled`, comparing what is there against what `http.sites` plus the application roles ask for — which needs a way for `cloud`, `spam`, `talk`, `fail2ban_ui` and `monitoring` to declare their vhosts, so it is a design change rather than a task.

* *Refreshing the apt cache is inconsistent between roles.* Five roles pass `update_cache: true` on their install task - `apt`, `dns`, `database`, `mail` and `spam`, plus `upgrade` for its own reasons - and the thirteen other package-installing roles assume the cache is already fresh, so running e.g. `playbooks/cron.yml` against a host where `playbooks/apt.yml` has never run fails with "No package matching 'cron' is available". The split is historical rather than decided, which is the part worth fixing: a reader cannot tell from a role whether it is meant to be self-sufficient. The molecule scenarios surfaced this, because they converge a role on its own; they work around it with a `prepare.yml`. It has never bitten `carcosa` because `apt.yml` is always run first, and an umbrella `site.yml` (see *No umbrella playbook* above) would encode that ordering properly. The alternative — `update_cache` in every role — is slower and duplicated, so this is a decision to make rather than an obvious fix.

* *The 26.04 upgrade is gated by Ubuntu, not by this repo.* `upgrade.target_release` is ready and `hastur` exists to rehearse it, but `do-release-upgrade` will not offer 24.04 -> 26.04 until the 26.04.1 point release. See `doc/TESTING.adoc` for what the rehearsal proved. Re-checked on 2026-08-16 and still not offered. Re-check with `do-release-upgrade -c`, rehearse on `hastur` again, then run it against `carcosa`.

== Documentation gaps

* No day-2 operations runbook: how to rotate the vault password, rotate a compromised user/mail password, restore a host from scratch, add a second host, or renew/replace host SSH keys. Three more have since been performed without being written down, and each has a non-obvious ordering that cost time to discover: rotating a TSIG secret (two-ended and with no rollover — the console must be updated or transfers stop, and a green playbook run does not prove they still work), rolling a DNSSEC key (the DS in the parent must be published *before* the old key stops being served, or the zone goes bogus rather than unsigned), and seeding the RSpamd Bayes classifier from an imported corpus (never re-run a bulk seed to chase a shortfall). `doc/STATUS.adoc` records what was learned in each case next to the thing it explains, but none of it is a procedure anyone could follow under pressure.
* The backup/restore procedure is documented in `doc/BACKUP.adoc` and has never been followed end to end. The restore *order* is the part most likely to cost time under pressure, and three of its steps are traps rather than sequence - `roles/spam`, `roles/cloud` and `roles/http` each generate a missing artefact and report success, so restoring the DKIM keys, `config.php` or `/etc/letsencrypt` after the role has run is too late. None of that has been rehearsed.
* `doc/environment-setup.adoc` covers the Dev Container only — there's no doc for the target *production* host prerequisites (base OS version/image, disk layout, initial bootstrap access before Ansible can connect, DNS delegation setup for the zone/aliases).
* No changelog or versioning convention for the infrastructure itself (e.g. how config drift or emergency manual changes on the host get reconciled back into the repo).

== Process / quality

* *The alert rules are only validated on the host, not in CI — and the case for fixing that is now demonstrated rather than argued.* `roles/monitoring` runs `promtool check rules`, `promtool check config` and `amtool check-config` as `validate:` steps, so a bad file is never installed — but that happens at deploy time, on the target. The static tests already render every template; running promtool over the rendered output would move the check earlier at almost no cost, and `promtool test rules` goes further still, unit-testing an alert expression against synthetic series with no host involved.
+
Both were done *by hand* for the probe and zone rules added on 2026-08-20, and both earned their keep immediately: a draft rule named a blackbox metric that does not exist, and `NsdZoneNotPropagated` depends on PromQL vector matching that would have produced no result at all, silently, had it been wrong. Neither is detectable by any check this repo runs today. That is the argument in one sentence — an alert rule that can never fire is exactly the silent failure the `postfix` fail2ban jail turned out to be, and this is the one part of the stack where it can be caught offline.
+
The obstacle remains tooling rather than effort. It needs promtool in `.devcontainer/Dockerfile` and in both workflows; the awkward part that used to make that hard is gone, since promtool now comes out of the same pinned upstream tarball as the server rather than from a package that differs between 24.04 and 26.04. Note the one wrinkle a CI job has to handle: the rules are rendered conditionally, so `zones.rules.yml` only exists where `monitoring.textfile.nsd.enabled` is set and its DNSSEC rule only where `nsd.dnssec.enabled` is — and the test inventory has DNSSEC off, so that branch renders in CI only if the job is told to vary it.

* *No cross-role or full-stack testing.* Static tests and molecule both check a role in isolation, but the bugs that have cost the most here were interactions between roles: `iptables-restore` flushing fail2ban's chains, the `http` certificate bootstrap deadlocking against nginx, a certificate lineage name disagreeing with what three other roles read. Half of what this item asked for now exists: the throwaway machine is a local QEMU/KVM guest rather than a rented instance (`.claude/skills/testlab/vm.sh`, a pristine cloud image per `reset` and free), `lab.sh deploy` runs the playbooks in dependency order against it, and `lab.sh verify` asserts an end state rather than an exit status - units running, loopback services on loopback only, `sshd -T`/`nginx -t`/`postfix check` clean, the packet filter at DROP, and a TLS handshake. That is the `goss`/`testinfra` shape written in shell, and it is what found the two bugs no other layer could (`sievec` compiled without `-c`, and `fail2ban` starting before nginx has created the logs its jails watch).
+
What is left is the automation rather than the capability: `playbooks/site.yml` so the order lives in the repo instead of in a skill script; the three playbooks that script's default order omits (`nsd`, `fail2ban_ui`, `talk`); and running the whole thing unattended rather than by hand. A rented Hetzner instance per run remains the option for anything the local guest cannot show - real hardware, a real public address, and therefore a real certbot. See `doc/TESTING.adoc`.
* *Only `monitoring` has a `verify.yml`, and the other six scenarios still prove convergence alone.* Written on 2026-08-20, after the discovery that `doc/TESTING.adoc` had been describing its checks for some time while molecule reported `verify: Missing playbook` on every run and the scenario passed regardless. The other six are not equally worth one — `apt`, `cron`, `time` and `users` have little end state a container can meaningfully interrogate — but `sshd` and `system` do: `sshd -T` denying root login and password authentication is exactly the kind of assertion that belongs there, and `lab.sh verify` already makes it on the VM. Worth lifting the two that overlap rather than writing six.
* *Molecule covers seven roles, and the rest are blocked for concrete reasons.* `doc/TESTING.adoc` holds the list and the per-role blocker; it is not repeated here, so that there is one place to update when a scenario is added. The short version is that `firewall` and `docker` want real netfilter and nested Docker, the service roles want real certificates and real cross-service communication, and `upgrade` reboots. `monitoring` was the most recent addition and is the one scenario that checks more than convergence; its Grafana half is skipped by tag, for the same Docker-in-Docker reason as `fail2ban_ui`. Adding a scenario means adding the role to the matrix in `.github/workflows/test.yml` as well, which discovery does not do for CI.
* A from-scratch provision has never been proven end-to-end *in one run*, though the machine to do it on now exists. `vm.sh reset` throws away a qcow2 overlay and re-runs cloud-init, so every lab run starts from a genuinely pristine 24.04 image — the caveat that used to apply to the whole `testlab` group is now true of `nyarlathotep` only, which was part-configured before it was adopted (and whose `lab.sh reinstall-stage`/`reinstall-arm` path is still **unverified and able to strand a machine with no console**). Roles have converged on a pristine guest in groups, and doing so found real defects; what has not happened is a single unattended run of every playbook against a fresh image ending in a host that serves. That is the same missing piece as the item above, seen from the other end. (`inventories/test/` is not this either: it is fake data for the tests and is never deployed.)
