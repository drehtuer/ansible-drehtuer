= Testing
include::.attributes-page.adoc[]

How this repository is tested, what each layer actually catches, and what it deliberately does not.

Nothing here replaces reading the output of a real run. The point of the automated layers is to make the *first* real run boring.

The dev container holds two sets of collections, which is deliberate
and occasionally confusing. The distribution's `ansible` package ships
around fifty of them inside `/usr/lib/python3/dist-packages`, found
through `sys.path`; the image additionally installs three from Galaxy
into `/usr/share/ansible/collections`, because molecule runs from a
virtualenv with an ansible-core of its own that cannot see the first
set.

`ansible.cfg` drops `/usr/share/ansible/collections` from its search
path so the repo's own runs see one copy of each rather than two -
otherwise every invocation warned three times that a second copy had
been found. The copy actually used was always the distribution's, so
the Galaxy ones were only ever noise outside molecule. Molecule is
unaffected: it generates its own `ansible.cfg` and never reads the
repo's.

== Layers

[cols="1,3,1", options="header,autowidth"]
|===
| Layer | What it does | Where it runs

| Linting
| `yamllint`, `ansible-lint` (`production` profile) and `ruff`. Style and Ansible idiom only — it never evaluates a variable or renders a template.
| CI + local

| Static tests
| Validates every `meta/argument_specs.yml` and renders every template against a fake inventory. No host is contacted, nothing is installed.
| CI + local

| Molecule
| Converges a role inside a systemd container and runs it a second time to prove it is idempotent.
| CI + local

| Deployment test
| Runs the real playbooks against a disposable host - by default a local QEMU/KVM VM, optionally a physical LAN machine - and resets it afterwards.
| Local only

| Drift check
| Runs the real playbooks against the real hosts in `--check --diff` mode and reports what differs.
| Local only

| Manual
| A real run against `carcosa`, and whatever cannot be automated at all.
| Local only
|===

== Test data

Everything the tests need lives in `inventories/test/`, and all of it is fake and deliberately *not* vault-encrypted:

* `testhost` does not exist, the domain is `test.invalid`, and the addresses are from the documentation ranges (RFC 5737 / RFC 3849).
* Passwords are throwaway strings, and the SSH key is a throwaway pair.

That is what lets the tests run in CI, which has no access to `vault/secret.txt`. It also means **the test inventory must be kept complete**: templates are rendered from it alone, without role defaults, so a template referencing a variable the test inventory does not define fails the static tests. That is intentional — it keeps the file a working example of what every role expects as input.

The molecule scenarios carry their own small set of values inline in `converge.yml`, so that `molecule test` works on its own from a role directory. That is a little duplication, accepted in exchange for each scenario being self-contained.

The two layers therefore read a role's inputs from opposite ends, and that is worth knowing before a failure looks mysterious. The static tests validate the argument spec against `inventories/test/`, which supplies every key; some molecule scenarios — `monitoring` is one — pass almost nothing and run the role on **its own defaults**. So a new required option in `meta/argument_specs.yml` that is added to the inventories but not to `defaults/main.yml` passes `invoke test-static` and fails `molecule converge` with *"missing required arguments"*. Adding an option means touching both.

== Static tests

[source, bash]
----
invoke test-static
----

Two checks, both in `tests/static.yml`:

*Argument specs.* Every `roles/*/meta/argument_specs.yml` is validated against the test inventory. This catches a role and its inventory drifting apart, and in particular the trap that has caused the most trouble here: overriding a role's top-level dictionary in `group_vars` *replaces* the role default rather than merging into it, so an override that forgets a single key breaks the role at run time.

*Template rendering.* Every `*.j2` in every role is rendered. This catches Jinja errors and undefined variables without needing a host. Three templates get extra attention, each because a conditional branch is where silent wrong-output bugs have actually lived:

* The firewall rules are rendered twice, for IPv4 and IPv6, and the test asserts that the two outputs actually differ — that branch previously compared a string against an integer and silently emitted the IPv4 ruleset into the IPv6 file.
* The `nsd` zone template is rendered once per entry in `nsd.zones` rather than only for the first, and the test asserts that `tsig.conf` renders as many distinct key names as there are zones. The role used to emit one transfer key for the whole server; one key per zone is what Hetzner's naming scheme forces, and a template regressing to a single shared block would otherwise render perfectly valid config that no secondary could use. The test inventory carries two zones for exactly this reason.
* The Grafana dashboards are parsed as JSON after rendering, and `roles/monitoring`'s `uptime.json.j2` is rendered a *second* time with the blackbox probes and every service exporter switched off. Its probe and self-report panels are conditional, so the test inventory - which has all of them on - exercises one branch only, and the other is exactly where a stray comma would sit. What that catches is quiet by nature: Grafana logs a malformed dashboard and carries on without it, so a broken file is a missing page rather than a failed run. The role validates the same thing with `validate:` at deploy time; this is the check moved to where it costs nothing and needs no host.

These tests are quick and need no container, which is why CI runs them before anything else.

== Molecule

[source, bash]
----
# Every role that has a scenario
invoke test-molecule
# Or a single role
invoke test-molecule --role=users
# Or directly, from the role directory
cd roles/users && molecule test
----

`molecule test` creates a container, converges the role, **converges it a second time and fails if anything reports changed**, then destroys the container. That idempotence step is the most valuable thing here: it is what catches a `creates:` guard that never matches, a `command` without `changed_when`, or a `when` condition that is always true.

=== Why the container image matters

Almost every role uses `systemd_service`, which does nothing useful in a container that is not running systemd as PID 1. The scenarios therefore use an init-enabled image (`geerlingguy/docker-ubuntu2404-ansible`) started with `/lib/systemd/systemd`, `privileged: true` and the host cgroup namespace. A plain `ubuntu:24.04` image will not work.

The Dev Container needs access to a Docker daemon for this — the host's own, reached over a bind-mounted socket (see `doc/environment-setup.adoc`), not one running inside the container. `invoke test-static` does not need it. Talking to that socket needs `sudo` unless the current shell postdates the container's group-membership fixup; see the same doc.

=== Which roles have scenarios

`apt`, `cron`, `users`, `sshd`, `time`, `system` and `monitoring` today. Adding one means creating `roles/<role>/molecule/default/` with three files:

* `molecule.yml` — the container definition. Note the `ANSIBLE_ROLES_PATH` it sets: molecule does not put the repository's `roles/` directory on the roles path, so without it the role cannot be resolved by name and the run fails at the `syntax` stage.
* `converge.yml` — the play that applies the role, with any variables it needs inline.
* `prepare.yml` — refreshes the apt cache. The images ship with an empty one, and of the roles with a scenario only `apt` refreshes it itself, so a role installing a package it does not already have cannot resolve it. (Five roles do pass `update_cache` — `apt`, `dns`, `database`, `mail`, `spam` — and the inconsistency is itself an open item. See `doc/TODO.adoc`.)

`invoke test-molecule` discovers scenarios rather than keeping a list. The CI matrix in `.github/workflows/test.yml` does keep a list, so add the role there too.

Two more patterns worth knowing about, both used to keep a role's *production* behavior completely unchanged while still letting it converge in a container:

* **A container-only test fixture, generated and torn down by the scenario itself.** `sshd` needs `files/ssh_<hostname>_*.aes256` to exist, and the real ones are vault-encrypted (CI has no vault password). `roles/sshd/molecule/default/prepare.yml` generates a throwaway key pair straight into the role's `files/` directory instead — `copy`'s `decrypt: true` is a no-op on content that is not actually vault-encrypted, so a plain key works despite the `.aes256` name. `cleanup.yml` removes it again; that stage runs both before `create` and after `verify` in the standard sequence, so an interrupted previous run self-heals rather than leaving stray keys behind. `.gitignore` covers the same filename as a second line of defense.
* **Skipping one production task inside the container only, via a tag.** `system`'s "Set hostname" task fails even under `privileged: true` (`sethostname()`: "Device or resource busy" — a real Docker limitation, not a config gap). It carries a dedicated tag, and the scenario's `provisioner.options.skip-tags` skips it — the real playbooks never pass `--skip-tags`, so it fires normally on a real host. This only works for *tasks*: a *handler* keeps running when notified even if its own tag is in `--skip-tags` (verified against ansible-core 2.20.1 — tag filtering only ever gates whether a task runs and can notify, not whether a notified handler itself runs). `time`'s "Set HW clock" handler was assumed to need this same treatment, but turned out not to: `hwclock --systohc` works fine here, because these containers already run `privileged: true` with the host's device nodes, RTC included — a plain, unprivileged container is what the old blocker below actually described.

`monitoring` covers only its collection half. The Grafana tasks sit in a block tagged `grafana`, which the scenario skips through `provisioner.options.skip-tags` — the same device `system` uses for setting the hostname. That half needs a Docker daemon and a running nginx, which is the Docker-in-Docker-in-Docker blocker `fail2ban_ui` has; what is left is still where the idempotence risk lives.

Otherwise `monitoring` is the one scenario that checks more than convergence, because it can: the whole stack is loopback services with no certificate and no cross-host traffic, so the container can be interrogated afterwards. It is the only role with a `verify.yml`, and until 2026-08-20 it did not have one either — this paragraph described the checks below for some time before anything ran them, which is worth recording as the exact failure this repo keeps warning about in other people's software. Molecule reported `verify: Missing playbook` on every run and the scenario passed regardless.

What it now proves: all three listeners are on `127.0.0.1` *and on nothing else* — both halves asserted, since a wildcard bind contains the loopback address and only the absence of `0.0.0.0` and `[::]` says the override took; that nothing holds Alertmanager's HA gossip port; that all three scrape targets are `up` and that the count is three, which is what would catch a scrape job silently dropped from the rendered configuration; that exactly the expected rule groups load - four of them since `roles/backup` added one - with every rule reporting `health=ok`, a different claim from promtool's — promtool proved the file parses before it was installed, this says Prometheus can evaluate each expression against real data; that the `Watchdog` is firing and is the *only* alert firing, so a rule misfiring on an idle machine is caught here rather than on a real one; and that the alert reaches Alertmanager and is routed to its mail receiver — where delivery fails at the SMTP connection, which is the correct outcome in a container with no Postfix and is what shows the routing is real rather than merely syntactically valid. A notification that was never attempted leaves that counter at zero, which is what a route matching nothing looks like.

Two negative assertions close it: neither the blackbox exporter nor the `nsd` collector may be listening, because both reach off the container — one probes real names, the other queries the delegated nameservers — so a default that quietly turned either on would make this scenario depend on the internet. `prepare.yml` installs `iproute2` for the socket checks, a test dependency rather than a role one.

**Writing it caught a metric that looks right and does not move**, which is worth recording because it is the same failure this document keeps describing in other things. The obvious counter for "delivery was attempted and failed" is `alertmanager_notifications_failed_total`, and it is the wrong one: Alertmanager retries a failing notification for the whole of the route's `group_interval` and only counts it failed once it gives up — so on the Watchdog route, whose interval is 24 hours, it reads zero for a day while delivery is plainly failing. Measured rather than reasoned about: 13 attempts recorded against 0 failures. The check now reads `alertmanager_notification_latency_seconds_count`, which moves per attempt, and asserts the SMTP failure separately from Alertmanager's own log. A first draft of this file passed its own review and failed against a real container, which is the argument for this layer in one sentence.

The assertions were also proven non-vacuous rather than assumed, by binding a wildcard listener on 9094 in a converged container and confirming `molecule verify` fails on it with the sockets printed.

It also earned its keep immediately by failing: `promtool` is a separate package on 26.04 but ships inside `prometheus` on 24.04, and the role installed it by name. The static tests could not have caught that — they never resolve a package — and neither could either linter. See `doc/STATUS.adoc`.

The rest are not covered, for concrete reasons rather than lack of effort:

[cols="1,3", options="header,autowidth"]
|===
| Role | Blocker

| `firewall`, `docker`, `fail2ban_ui`
| netfilter and Docker-in-Docker-in-Docker. These want a VM - which is where `fail2ban_ui` was in fact verified, see below.

| `http`, `cloud`, `mail`, `imap`, `spam`, `dns`, `database`
| Need real certificates and real services talking to each other. See <<Not covered>>.

| `upgrade`
| Runs `do-release-upgrade` and reboots. Not meaningfully automatable.

| `backup`
| Wants a real MariaDB to dump and a real Nextcloud to quiesce, which is the same blocker as the row above it. What was done instead is recorded below.
|===

This table is the single record of what molecule covers and why the rest is not covered; `doc/TODO.adoc` points here rather than repeating it. Update it here when a scenario is added.

*`backup`'s scripts were tested standalone instead, and it is worth saying exactly what that is worth.* The two rendered scripts were run in the dev container against a scratch `restic` repository - initialize, back up, honour the exclude file, prune to the retention policy, verify with `restic check`, then destroy the source tree and restore it, comparing every restored file byte-for-byte against the original. That is a real end-to-end exercise of the half of the role that is shell.

It found three defects, and the reason to record them is that *none of them would have failed a playbook run*: `occ` was called from a shell trap without its own working directory, so maintenance mode would never have come off; an empty database list was skipped rather than refused, so an unreachable MariaDB would have snapshotted the previous day's dumps and reported success; and the snapshot count was read with `grep -c` over single-line JSON, which answers 1 however many snapshots exist. A converge-only scenario would have reported green on all three.

*The role was then deployed to `yuggoth` on 2026-08-22, and the run closes what the standalone exercise could not.* It converged and reported `changed=0` on the second run. `systemctl start backup.service` dumped both databases - `mysql` and `nextcloud`, correctly leaving the three system schemas out - held maintenance mode around the dump and *left it off afterwards*, which is the trap fix above confirmed against a real Nextcloud rather than reasoned about. Six paths were snapshotted, the retention policy applied, and the metrics written.

The restore was then performed rather than assumed. A home file, a DKIM private key and a database table were deleted and dropped, then restored from the snapshot: both files came back byte-identical by SHA-256 and, the part worth checking separately, with ownership and mode intact - `_rspamd:_rspamd 0600` on the DKIM key, which rspamd refuses to use if it is wrong. The database was reloaded from its own dump with `restic dump ... | gunzip | mariadb`, the dropped row was back, and Nextcloud still reported `installed: true` afterwards.

*The alert rules were proven non-vacuous in both directions*, which matters more here than the fact that they load. Backdating the success timestamp past 36h took `BackupStale` to `pending` while the other two stayed inactive. Removing the metric file entirely then took `BackupStale` back to *inactive* - because `time() - <absent>` is an empty vector and cannot fire - while `BackupMetricsMissing` went `pending`. That is the whole argument for the third rule, demonstrated rather than asserted: the obvious staleness alert is blind to its own worst case.

*One defect only the real run could surface.* A systemd unit inherits no `HOME`, so restic could not locate a cache and logged `unable to open cache` on every invocation while carrying on. Correct output, and increasingly expensive as the tree grows. The units now set `CacheDirectory=restic` and `RESTIC_CACHE_DIR`; after redeploying, the warning is gone and `/var/cache/restic` is populated.

*The lab then appeared to give a false pass, and the eventual explanation was the opposite of the first one — which is the most useful result in this section.* The database dump ran happily on `yuggoth` and was refused on `carcosa`. The script connected to MariaDB as root with no password.

The first reading written down here was that `yuggoth`'s root account had "no password" and was therefore accidentally permissive. That was wrong, and it took provisioning a genuinely pristine guest to see it: `yuggoth` carried Ubuntu's default, `mysql_native_password` with the placeholder string `invalid` — which can never match — *OR* `unix_socket`, which matches the system root user. Secure, not open. The 7-character `authentication_string` that first drew attention is the word `invalid`.

So the lab was correct and **production had drifted**: `carcosa`'s `root@localhost` had been changed to password-only with the socket alternative removed, and no `root@127.0.0.1` existed there, while the role produced the reverse on a fresh host. Neither reproduced the other. `roles/database` reconciles both to socket-plus-password now, and `doc/STATUS.adoc` carries that.

The lesson survives the correction, only pointed the other way: a lab pass and a production failure meant the *lab* was right, and the instinct to trust production as the reference would have led to hardening the wrong host. Nothing short of provisioning a pristine guest and reading `mysql.global_priv` directly could tell which.

Deployed to `carcosa` on 2026-08-22 with the fix, where the first backup read 201913 files and 103.4 GiB in 29 minutes and a restore was verified against the live copies. `doc/STATUS.adoc` carries those numbers.

== Deployment test

**`playbooks/site.yml` is the order now, not `lab.sh`'s `PLAYBOOKS` array.** That array was the tested order and is what `site.yml` was built from, but it lived in a skill script rather than the repository, and it omitted `nsd`, `fail2ban_ui` and `talk` - so "every playbook, in order" meant seventeen of the twenty roles a rebuild needs. It also ran `fail2ban` eighth, before the roles that create two of the logs its jails watch, which left the service dead on every lab deploy it ever performed.

Deploying a whole guest is one command now:

[source, bash]
----
.claude/skills/testlab/vm.sh reset
.claude/skills/testlab/lab.sh seed-certs
invoke run-playbook --playbook=playbooks/site.yml --hosts=yuggoth
----

`nyarlathotep` is a LAN-only physical machine in the inventory's `testlab` group. It is what molecule and the static tests cannot be: real hardware, real systemd, real services talking to each other, with every role applied in order rather than one at a time. It is disposable — nothing on it is backed up, and it is rolled back between runs.

Everything runs through `.claude/skills/testlab/lab.sh`; see that skill's `SKILL.md` for the full workflow, the lockout hazards and the reinstall path.

[source, bash]
----
# the VM, which is the default target
.claude/skills/testlab/vm.sh  create     # pristine guest, booted
.claude/skills/testlab/lab.sh deploy     # every playbook, in order
.claude/skills/testlab/lab.sh verify     # units, sockets, validators, TLS
.claude/skills/testlab/vm.sh  reset      # pristine again, in seconds

# the physical machine
LAB_TARGET=metal .claude/skills/testlab/lab.sh snapshot
LAB_TARGET=metal .claude/skills/testlab/lab.sh deploy
LAB_TARGET=metal .claude/skills/testlab/lab.sh reset
----

Two things make this work at all:

*Certbot is never reached.* The machine has no public DNS and no inbound internet, so Let's Encrypt cannot validate it. `lab.sh seed-certs` installs a self-signed certificate carrying exactly the names the `http` role computes, and the role's SAN comparison then finds nothing to do. This is the *reason* that role compares names rather than checking whether a certificate merely exists.

*The rollback is an LVM snapshot.* Root is a logical volume with ~829 GB free in the volume group, so a snapshot the size of the whole origin costs nothing and can never overflow. `reset` merges it and reboots; the merge completes during boot, and the baseline is re-taken afterwards because merging consumes it. `/boot` is a separate partition outside the snapshot, so it is archived and restored alongside — not as a backup, but so root and `/boot` never disagree about which kernel is installed.

*`http` and `cloud` are verified on the VM, and finding a real bug is what that took.* Both roles converged and reported `failed=0` on the first run, and Nextcloud was nonetheless a 502: the PHP-FPM pool template started with `{{ ansible_managed | comment }}`, whose `#` decoration is fatal to php-fpm's pool parser, so the service never started and its socket never appeared. `template` has no validator, and the reload handler reports success even when the service dies behind it - so nothing in the run went red. The role now runs `php-fpm -t` for the same reason it already runs `nginx -t`, and that guard was tested by reinstating the broken header and confirming the run fails at it.

With the fix, `https://cloud.<domain>/` and `https://<domain>/nextcloud/` both answer 200, `status.php` reports `{"installed":false,...,"productname":"Nextcloud"}` - the app runs; only the `occ` installer has not been executed - port 80 redirects, HSTS is served with the expected `max-age`, and both roles are idempotent. The certificate path was exercised too: the seeded self-signed SANs matched what the role computes, so certbot was skipped rather than attempted.

*Seven roles are verified on the VM.* `system`, `apt`, `users`, `sshd`, `time`, `cron` and `firewall` converge on a pristine 24.04 guest and are idempotent - a second pass reports `changed=0` for every one. The end state was checked rather than assumed: hostname and locale, the base package set, group membership and `%sudo NOPASSWD`, `sshd -T` denying root login and password auth, `ntpsec` active on Europe/Berlin, `cron` active, and `INPUT`/`FORWARD` at DROP in *both* address families with the expected ports open and rate limiting on 22. That last one confirms on a live host what the static test only asserts about the rendered template - the v4 and v6 rulesets really do differ.

Note that `sshd` cannot run on a host with no pre-generated key pair: `roles/sshd/files/ssh_<hostname>_*.aes256` must exist first, via `roles/sshd/scripts/generate_keys.sh <hostname>`. This is a gate on provisioning any new host, and it is what made `sshd` fail on `hastur`.

*The `upgrade` role has been run, and cannot currently succeed.* `hastur` is a 24.04 guest carrying `upgrade.target_release: "26.04"`, which is what the role needs to do anything at all. Running it gets as far as `do-release-upgrade` and stops there:

----
Current release 24.04, target 26.04, upgrade needed.
do-release-upgrade  FAILED rc=1
  "There is no development version of an LTS available."
----

That is Ubuntu's LTS gate, not a defect: 24.04 -> 26.04 is not offered until the 26.04.1 point release. Everything up to that point works - both assertions, the version comparison, the full upgrade of the current release, the prompt-mode change - as does the no-op path when the target is already reached (`ok=5 changed=0 skipped=8`). What remains unproven is a `do-release-upgrade` that actually completes, reboots and passes the closing assert. Rehearse on `hastur` once Ubuntu offers the upgrade, *before* pointing the role at production.

The run also surfaced a real defect, since fixed: the role read `ansible_distribution`/`ansible_distribution_version` as bare top-level variables, which ansible-core 2.24 deprecates in favour of `ansible_facts[...]`. Worth noting as the kind of thing only a real run finds — the deprecation is a run-time warning, so no linter and no static test could have reported it.

*`nsd`, `mail` and `imap` are verified on the VM, and the multi-domain behaviour with them.* All three converge on a pristine 24.04 guest and are idempotent. What was checked is the behaviour rather than the exit status:

* *Two zones, two transfer keys.* `nsd-control zonestatus` reports both zones as `master`, and `tsig.conf` carries two `key:` blocks with distinct names. An AXFR of each zone succeeds when presented with **its own** key, and `lab.test` is answered `REFUSED` when offered `lab.lan`'s key — which is what proves the keys are genuinely per zone rather than one key rendered twice. An unsigned transfer is refused, and a query for a foreign name is still `REFUSED` with no `ra` flag, so the multi-zone configuration has not turned it into a resolver.
* *One inbox across both domains.* Messages to the account at the primary domain, at the alias domain, and to `postmaster@<alias domain>` all arrive in the same Maildir; `postfix check` is silent. `doveadm user` resolves the account under either domain to the same uid and home, and an IMAP login succeeds with either — the same 7-message INBOX.
* *The old behaviour was reproduced before it was fixed.* Putting the previous `virtual_mailbox_domains`/`virtual_alias_domains` back and re-sending showed the alias-domain message leaving the host — `relay=none ... status=bounced (Host or domain name not found)` — rather than being refused, which is what corrected the account of it in `doc/STATUS.adoc`.

That run also found two defects that had nothing to do with the change being tested, both invisible on `carcosa` because they only bite a host being built from nothing: `sievec` compiled without `-c` and failed the whole `imap` role, and `fail2ban` starts before nginx has created the logs its jails watch and exits `255`. The first is fixed; the second is an ordering constraint recorded in `doc/TODO.adoc`. That is the argument for this layer in one paragraph.

*`rspamd-train-bulk` is verified on the VM, and the run corrected the tool it was testing.* A 200-message spam corpus and a 100-message ham one, generated with real headers, plus three messages with almost no body and two below the 256-byte floor. What it proves is the arithmetic on a real controller: the fresh corpus reported `learned 200, skipped 0, failed 0, unaccounted 0 of 200` and exited 0, the ham corpus the same at 100, and the reconciliation accounted for every path in each. Stopping rspamd made the pre-flight fail in **0.165 seconds** rather than after an hour of failing batches, and `rspamc -t 0.001` made even the pre-flight time out - which is also how the real wording of a timeout was confirmed to be `IO timeout`, matching none of the phrases the old grep-based counting looked for and therefore counted nowhere.

Two things only a real rspamd could have shown. Learning the same corpus a second time immediately had 188 messages refused and **12 learned again**, on an idle guest - the double-learn window, measured rather than argued for, at 6%; a third pass refused all 200. And `rspamc stat` **lags**: it answered `learned: 0` throughout the runs and reported 212 (200 + the 12 relearns, exactly right) only minutes later, after the service had been restarted. The script had been comparing that counter against its own count and warning when they disagreed, so it was confidently reporting that Redis had refused writes while Redis had done nothing of the sort. It now prints the reading and names the invariant instead, and the live value is `redis-cli hget RS learns_spam`.

*The `nsd` boot-order drop-in is verified by real reboots, in both directions.* A `systemctl restart` cannot test this at all - by then the addresses exist - so the guest was rebooted three times with the failure deliberately reproduced.

The reproduction is worth keeping: a `late-address.service` that sleeps 25 seconds after `network-online.target` and then adds `10.99.99.99/32` to `lo`, with that address added to `nsd.conf`. It turns the production race into something that happens on demand.

* *With the drop-in*, nsd failed to bind at `23:29:26`, was retried at 5-second intervals - `restart counter is at 1 … 5` - and the sixth attempt at `23:29:52.27` succeeded, 1.4 seconds after the address landed at `23:29:50.9`. Recovered unattended in 26 seconds, bound to both addresses.
* *With the drop-in moved aside* and nothing else changed, the same boot reproduced `carcosa` exactly: five attempts between `23:30:20` and `23:30:21.31`, then `nsd.service: Start request repeated too quickly`, and the unit sat `failed` while the address arrived 25 seconds later with nothing left to retry.
* *With the fix restored and the artificial address gone*, the ordering half shows on an ordinary boot: `Finished systemd-networkd-wait-online.service` at `23:31:32.36`, `Starting nsd.service` at `23:31:32.94`, `nsd started` on the first attempt - the reverse of the production order, where nsd started 3.5 seconds *before* the network was configured. Zero failed units, and the zone answers.

The role is idempotent over this: the run after the reproduction reported `changed=0`.

*The move to an upstream Prometheus is verified on the VM, and it caught a bug in the half that was already deployed.* Converged from the packaged 2.45.3 to upstream 3.14.0 in place: the service came up on the first attempt, bound to `127.0.0.1:9090` and nowhere else, all three scrape targets `up`, both rule groups loaded (6 and 12 rules), and the existing TSDB under `/var/lib/prometheus/metrics2` carried over rather than being started afresh. `/prometheus/` now redirects to `/prometheus/query` and serves the React bundle (a 1.9 MB `assets/index-*.js` fetched 200 under the prefix), while `/prometheus/classic/graph` is 404 — the reverse of the packaged server. nginx still answers 401 without credentials, and `nginx -t` is clean. The role is idempotent over the switch: `changed=0` on the following run, once a `stat` guard stopped it re-fetching the tarball every time.

The bug is the one no `curl` against nginx could have found. Grafana's provisioned datasource pointed at `http://127.0.0.1:9090`, without the route prefix Prometheus serves everything under, so a query through Grafana's own proxy returned `404 page not found` — and Grafana renders that as an empty panel, not an error. Confirmed identical on `carcosa` before fixing. The check that catches it is a query pushed *through* the datasource proxy, which now returns live series.

*The per-service exporters are verified on the VM, including one that is deliberately broken.* All nine scrape targets report `up` — node, prometheus, alertmanager, and the six services — with every exporter bound to loopback and nothing on a public address. The eight new rules load, evaluate `health=ok`, and each of their selectors was queried against the live host first, which is what distinguishes a rule that is quiet from a rule that is dead.

The check worth more than the rest was making one fail: stopping nginx took `nginx_up` to 0 within a scrape interval and moved `NginxDown` to `pending`, while `ServiceExporterDown` stayed inactive because the exporter itself was still answering. That is the distinction the two rules exist to draw, confirmed rather than assumed. Starting nginx again returned it to 1.

Two things the run caught that no linter could. `promtool` rejected the first rules file outright — an annotation may not *begin* with a Go template expression, since a YAML value starting with a brace is read as a flow mapping, and the parse error surfaces a dozen lines later. And the role was re-fetching the Prometheus tarball on every run until a `stat` guard was added, which only a second consecutive deploy shows. All three roles report `changed=0` on a re-run.

*The textfile collectors and the second dashboard are verified on the VM, including by making the numbers move.* Both collectors write their `.prom` files, both timers fire every minute, `node_textfile_scrape_error` is 0, and all five panel expressions return series. Grafana lists the new dashboard with its four panels, and a panel query pushed through Grafana's own datasource proxy comes back with data.

The check that matters is the one where the metric had to move. Two failed SSH logins against the guest took `fail2ban_jail_failed_total{jail="sshd"}` from 0 to 2 and `failed_current` to 1, and the graph's own expression - `rate(...) * 60` - then read 0.157 failures per minute, which is two attempts spread over a fifteen-minute window. A graph fed by a collector nobody has watched move is indistinguishable from a graph fed by nothing.

*`fail2ban_ui` is verified on the VM.* It converges, is idempotent over two runs, and the end state was checked rather than assumed: the container runs the pinned digest, `ss -ltn` shows it bound to `127.0.0.1` and nothing else, nginx answers 401 without credentials and 200 with them, and the container can read both `/var/run/fail2ban/fail2ban.sock` and `/etc/fail2ban`. `/api/settings` returns live JSON through the proxy, which is what proves the reverse proxy and the app agree rather than merely that a port is open.

Two interactions were worth testing separately. Restarting Docker - which `playbooks/firewall.yml` does on every rules change - leaves the container untouched thanks to `live-restore`, and a full `firewall.yml` run afterwards left the UI answering. And the certificate: adding `f2b` to `http.letsencrypt.subdomains` means `lab.sh seed-certs` has to be re-run before `http.yml`, or the SAN comparison finds a mismatch and tries to reach certbot.

*`monitoring` is verified on the VM, and the mail path is the reason it had to be.* The role converges and is idempotent there — a second run reports `changed=0` — with all three listeners on loopback, nothing on Alertmanager's 9094, and `lab.sh verify` green for the three units and three ports it now checks. What only a machine with a mail server could show is the rest of the chain: the `Watchdog` alert fired, Alertmanager routed it, Postfix accepted it on loopback and Dovecot delivered `[FIRING:1] Watchdog (yuggoth watchdog)` into the Maildir over LMTP. The molecule scenario reaches the SMTP connection and correctly fails there, having no Postfix, so this is precisely the seam between the two layers.

The more interesting check was of the alert rules themselves. `promtool` proves an expression parses, not that the metric it names exists — and a rule selecting a metric that never appears is silently incapable of firing, which is the `postfix` fail2ban jail's failure exactly. Every selector was therefore queried against the live host and all returned series, the fact-derived network interface included. That check costs one HTTP request per rule and is worth repeating whenever a rule is added; it is the only thing that distinguishes a rule that is quiet from a rule that is dead.

*Grafana is verified on the VM, and one of its failure modes is browser-only.* The role is idempotent there, the container binds `127.0.0.1:3000` and nothing else, the superseded `status.conf` is gone, nginx answers 401 without credentials and serves Grafana's login page with them, and both the datasource and the dashboard are provisioned. The check worth more than all of those is a query pushed *through* Grafana's own datasource proxy, which came back with live series: that is what proves Grafana can reach a Prometheus which has no vhost of its own, rather than merely that both processes are running.

Two things were found here that no amount of `curl` would have reported on its own, and both are written up in `doc/STATUS.adoc`: nginx forwards the basic-auth `Authorization` header upstream, where Grafana reads it as a failed login and sends the browser into a re-prompt loop; and Grafana cannot run under the shared CSP, which returns 200 and renders an empty page. The first is now visible as a 302 to `/login` instead of a 401, and the second as exactly one CSP header carrying `'unsafe-eval'` and `blob:`. Whether the interface actually *draws* still needs a browser, and is the one claim this layer cannot make.

*This is not a substitute for a from-scratch provision.* The metal machine is not pristine — several services predate the skill — so a green run proves the roles converge and the services come up, not that a bare Ubuntu install would reach the same place. That gap is the *No cross-role or full-stack testing* item in `doc/TODO.adoc`.

== Drift check

[source, bash]
----
invoke check-drift
# Or a single playbook
invoke check-drift --playbook=playbooks/sshd.yml
----

Runs the real playbooks against the real hosts with `--check --diff`, changing nothing. Anything reported is a difference between this repository and the host — usually a manual change made during an incident that was never written back. Running it weekly is a reasonable habit.

*This cannot run in CI*, because it needs the vault password and SSH access to the host. It is a local task on purpose.

Read the output rather than only the exit code. Check mode is not a clean pass/fail signal: a task whose result depends on an earlier task having actually run — a `command` guarded by `creates:`, or anything reading a file a previous task would have written — is reported as changed, or fails outright, on a host where that earlier task really did already run. The task exits non-zero if any playbook reports problems, which is a prompt to look, not proof of drift.

== Not covered

Worth being explicit, so the green ticks are not read as more than they are.

*Cross-role interaction.* Every layer above tests a role, or a template, in isolation. The bugs that have actually cost the most here were interactions: `iptables-restore` flushing fail2ban's chains, the `http` role's certificate bootstrap deadlocking against nginx, one role's certificate lineage name disagreeing with what three other roles read. Catching those needs a full run against a throwaway VM, which is the obvious next step and is not built yet — see `doc/TODO.adoc`.

*Anything requiring a real certificate.* Certbot cannot work against a container. A VM-based layer would need a test subdomain pointed at it and Let's Encrypt staging, or a local ACME server such as Pebble.

*Whether the services actually work.* Molecule proves a role converges and is idempotent. It does not prove nginx serves the right vhost, that mail is delivered, or that a fail2ban jail matches anything. A `fail2ban-client status <jail>` assertion after a real run is worth more than any of the above for that particular class of problem.
